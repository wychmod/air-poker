# 开发与交付流程

## 1. 定位任务

开始时查看 Git 状态、README、文档索引和相关源码，写清本轮目标与通过条件。识别已有修改及待评审提案，保持它们的内容与提交边界。当前用户指令优先于旧任务记录。

小型文档或局部修复可直接实施，不要求重复走多轮审批。跨模块或规则改动先使用 [任务模板](task-template.md) 记录范围、依赖和验收条件；只有缺失信息会实质改变工作方向时才澄清。

涉及第三方技术的具体用法时按根 `AGENTS.md` 的 Context7 规则查证文档；业务规则以当前代码、测试和用户需求为依据。

## 2. 选择修改位置

- 牌面与目标模板：数据层。
- 比较、有效牌、资金计算：纯规则层。
- 阶段、合法动作、对局状态：引擎。
- 界面结构与显示：渲染模块；文案放入 i18n。
- 事件、计时、存储、页面切换：入口层。
- 工程校验：harness；发布清单：统一配置及打包脚本。

按职责拆分，避免把计算搬进 DOM 模板，或为了检查通过把浏览器依赖藏进游戏层。新增模块应调整明确的依赖矩阵，不整体关闭检查。

## 3. 形成反馈循环

1. 缺陷先用输入、动作序列和期望结果描述；涉及规则或状态时优先增加可复现测试。
2. 实现最小范围改动，运行相关测试，修正失败。
3. 更新发生变化的工程事实、接口和验收记录。
4. 运行 `npm run check`，读取真实结果与首个失败原因；全部通过后不无目的重复运行。
5. 如果修改涉及页面交互或浏览器 API，执行 [浏览器验收](acceptance.md) 的相关场景。

纯文档修改不需要虚构新的业务测试；修改检查器本身则需要证明典型坏例会失败，防止检查只是“始终绿色”。不要通过降低断言、删测试或放宽全部规则掩盖回归。

## 4. 记录证据

自动报告 `output/harness/latest.json` 包含运行环境、开始/结束时间、每步命令参数、耗时、退出码与通过状态。某一步失败后后续不执行，必须先定位失败再交付。

任务记录应说明执行了哪些命令、结果、浏览器及视口、相关交互结果和未执行项。浏览器截图及临时输出放入忽略目录，必要时提供明确路径。自动资源检查通过只能证明它覆盖的静态引用可加载。

## 5. 提交与发布

用户明确要求提交时才提交；明确要求推送时才推送。先检查 `git diff` 与 `git status`，再使用显式路径暂存，审查 `git diff --cached`，防止带入用户未评审的方案或其他任务的修改。

新增静态资源先更新统一发布清单，检查生成产物并补浏览器验证。GitHub Pages 上传 `dist/site/`；不整仓上传，也不把本地设计预览误当作正式页面发布。

交付用中文说明最终改动、原因、验证结果、剩余限制及文档位置。没有执行的 CI、部署或浏览器测试不得宣称成功。
