# AIR POKER Harness

这套 harness 将项目知识、修改边界、自动反馈和验收证据放进仓库，使开发者能在不依赖聊天历史的情况下理解项目并验证改动。它是当前静态项目的开发基础设施。

## 最短路径

```sh
npm ci
npm run check
npm start
```

`npm run check` 逐项执行，失败立即停止并返回非零状态：

| 步骤         | 检查内容                                                         | 发现问题后看哪里                       |
| ------------ | ---------------------------------------------------------------- | -------------------------------------- |
| syntax       | 运行源码、脚本、测试能否被 Node 解析                             | 命令输出的文件与语法错误               |
| architecture | AST 解析导入、依赖层级、循环、平台 API 和入口内联事件            | `scripts/harness/config.js` 与违规模块 |
| tests        | 游戏规则、状态、资源性质与 harness 反例                          | `tests/` 中失败用例                    |
| format       | 受管理源码、配置、工程文档的 Prettier 格式                       | 运行 `npm run format` 后审查差异       |
| build        | 按显式清单生成 `dist/site/`                                      | 发布清单与文件是否存在                 |
| http-smoke   | 递归解析入口引用，检查本地资源、MIME、响应体大小与非站点文件隔离 | 缺失路径与引用源                       |

HTTP 检查使用动态端口的临时服务器，分别模拟 `/` 与 `/air-poker/` 托管路径，结束后关闭服务。外部字体等远程地址跳过，不依赖联网；页面脚本不会被执行。需要真实浏览器的场景见 [验收清单](acceptance.md)。

## 文件与证据

| 路径                         | 内容                                                   |
| ---------------------------- | ------------------------------------------------------ |
| `AGENTS.md`                  | 可直接加载的仓库协作约束                               |
| `doc/README.md`              | 知识索引与文档状态                                     |
| `doc/harness/`               | 架构、开发流程、浏览器验收、任务模板                   |
| `scripts/harness/config.js`  | 层级、源码范围、格式化范围、发布白名单、MIME           |
| `scripts/harness/`           | AST 检查、资源检查、一键执行与结果报告                 |
| `scripts/stage-site.js`      | 本地与 CI 共用的静态产物生成                           |
| `tests/harness.test.js`      | 验证违规依赖、平台耦合、循环与不安全资源路径确实被拒绝 |
| `output/harness/latest.json` | 最近一次完整命令的时间、环境、步骤、耗时、退出码与结果 |
| `dist/site/`                 | 可发布站点，只包含清单中的运行文件                     |

`output/harness/` 和 `dist/` 是忽略的生成内容。报告不是历史数据库，每次完整检查会覆盖最近结果；具体错误保留在终端输出。运行单个检查命令不会更新完整报告。浏览器证据按任务单独记录，不能用 HTTP 检查的通过冒充端到端测试通过。

## CI

- Pull request 和推送 `main` 运行 `.github/workflows/ci.yml` 中的完整检查。
- Pages 发布仍由 `.github/workflows/pages.yml` 负责；发布前再次检查，上传相同的 `dist/site/`。
- 两条工作流均采用锁文件安装，使用同一条 `npm run check`，避免本地与 CI 的校验清单漂移。
- CI 保存 `latest.json` 作为可下载 artifact，包含失败时已经执行的步骤；未执行步骤不会伪造通过。

本次只建立工程验证与协作基础，不实现待评审提案中的新游戏页面，也不规定 UI 风格。
